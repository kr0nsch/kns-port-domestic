# Перенос проекта CODESYS в Astra.IDE: оценка и выполнение

Пошаговая инструкция для инженера, которому нужно перенести свой проект CODESYS V3.5 в Astra.IDE
(РегЛаб, ПЛК REGUL) и заранее понять, сколько это стоит. Инструменты и документы — из этого
репозитория; пример — перенос флагмана КНС-1 и библиотеки plc-process-lib, сделанный ими же.

Что нужно: Python 3.11+ и git — для всех шагов, кроме сборки; Astra.IDE (и ВПЛК REGUL) — только для
сборки и испытаний. CODESYS не нужен, кроме эталонной проверки файлов импорта (по желанию).

## 1. Что делает каждый инструмент

| Шаг | Инструмент или документ | На какой вопрос отвечает |
|---|---|---|
| оценка | `tools/inventory.py` | какие возможности CODESYS используются в коде, где и с каким риском для Astra.IDE |
| оценка | [differences.md](differences.md) | как устроено в Astra.IDE и что решено; каждый факт — со ссылкой на документ РегЛаб |
| оценка | `tools/port_checks.py` (без `--fix`) | сколько мест кода зависит от каждого непроверенного пункта чек-листа |
| перенос | `tools/port_checks.py --fix` | маркер `// PORT: … проверить в Astra.IDE` у каждого такого места |
| перенос | `tools/port_metrics.py --strict` | сколько строк перенесено без изменений, изменено, переписано; помечена ли каждая правка |
| перенос | `tools/st_to_plcopen.py` | файл PLCopen XML для импорта в Astra.IDE |
| сборка | [BUILD_ERRORS.md](BUILD_ERRORS.md) | куда записывать сообщения среды и как их разбирать |
| сборка | `tools/port_checks.py --resolve` / `--fail` | что делать с маркерами, когда пункт проверен |
| всё | [migration_checklist.md](migration_checklist.md) | порядок работ: подготовка, библиотеки, ввод-вывод, связь, HMI, испытания, риски, пункты «проверить вручную» |
| сопровождение | `tools/upstream_delta.py` | что изменилось в исходном проекте и как перенести это в адаптированный код |

## 2. Свой код в раскладку

Инструменты читают исходники ST в раскладке [LAYOUT.md](LAYOUT.md): один объект CODESYS — один файл или
папка (`src/DUTs`, `src/GVLs`, `src/Interfaces`, `src/POUs`).

- Проект уже в раскладке (сделан из [plc-repo-template](https://github.com/kr0nsch/plc-repo-template)
  или его потомков) — ничего делать не нужно.
- Есть только `.project`: в CODESYS «Проект → Экспорт PLCopenXML…» для приложения, затем

  ```bash
  python tools/st_to_plcopen.py --reverse export.xml --to ../my-project
  ```

  Раскладка появится в `../my-project/src`. Что переносится через PLCopen XML, а что нет (визуализации,
  задачи, дерево устройств), — [plcopen.md](plcopen.md).

Дальше в примерах свой проект — `../my-project` (каталог с `src/`) рядом с клоном этого репозитория.

## 3. Оценка до переноса

### 3.1 Инвентаризация

```bash
python tools/inventory.py --source my=../my-project@HEAD --allow-missing --md build/my-inventory.md --json build/my-inventory.json
```

`@HEAD` — коммит git, из которого читаются файлы (`@worktree` — рабочее дерево как есть).
`--allow-missing` пропускает источники этого репозитория (библиотеку и флагман), если их рабочих копий
рядом нет. В отчёте `build/my-inventory.md` главная таблица — «Главные риски»: возможность, сколько мест,
ссылки на факты и пункты чек-листа, что делать.

### 3.2 Сколько мест зависит от каждого пункта

```bash
python tools/port_checks.py --tree ../my-project/src --config build/my-checks.json
```

Без `--fix` команда ничего не пишет: печатает места без маркера и сводку по пунктам чек-листа (пункт,
метка, мест по правилам). Правила (17 штук) — в начале `tools/port_checks.py`, полный список —
`python tools/port_checks.py --list-rules`. Файл решений `build/my-checks.json` пока не существует —
значит, все пункты открыты. Если в `targets/astra/port_checks.json` этого репозитория пункт уже отмечен
проверенным по сборке КНС-1, укажите этот файл в `--config`, и такие места пропадут из сводки.

### 3.3 Из сводки — в оценку

Инструменты не считают часы: они дают число мест по пунктам, а цену правки при отказе пункта знает
инженер. Удобная форма — таблица на каждый пункт сводки:

| Пункт | Мест | Если подтвердится | Если нет: что делать (по [differences.md](differences.md)) | Сложность правки |
|---|---:|---|---|---|
| C1 `EXTENDS`, `SUPER^` | | правок нет | наследование → композиция и интерфейсы | высокая: меняется структура ФБ |
| C3 `PRIVATE`/`PROTECTED`, свойства | | правок нет | убрать спецификатор; свойство → методы `GetX`/`SetX` | низкая, механическая |
| C5 `{attribute 'strict'}` | | правок нет | атрибут оставить, строгость проверяет сборка в CODESYS | нет |
| C7 перечисление с базовым типом | | правок нет | без базового типа, те же явные значения | низкая |
| C10 CAA File | | правок нет | ФБ записи файла на SysFile в низкоприоритетной задаче | средняя |
| C11 `LTIME` | | правок нет | источник времени на SysTime / `PsTimeGetUtcTimeNs` | средняя |
| C13 `VAR_IN_OUT CONSTANT` | | правок нет | `VAR_IN_OUT` с пометкой «только чтение» | низкая |

Пустые колонки заполняются числами из сводки. Отдельно — работа, которой нет в коде и которую
инструменты не видят: дерево устройств и модули ввода-вывода, Modbus, задачи, Persistent Variables,
символьная конфигурация OPC UA, визуализация, испытания (разделы 1, 3–6 [чек-листа](migration_checklist.md)).

## 4. Перенос

1. **Адаптированное дерево.** Скопировать `src/` своего проекта в `targets/<среда>/src` (как здесь —
   `targets/astra/src`) и не править оригинал. Снимок оригинала на коммите переноса — в `upstream/<id>/src`
   и запись в `upstream/SOURCES.json` (раздел 6): от него считаются метрики и дельта.
2. **Маркеры проверки:**

   ```bash
   python tools/port_checks.py --tree targets/astra/src --fix
   ```

   Над каждой строкой с непроверенной конструкцией появится, например:

   ```
   // PORT: [oop] проверить в Astra.IDE — наследование ФБ (EXTENDS) (C1)
   FUNCTION_BLOCK FB_MotorVfd EXTENDS FB_Motor IMPLEMENTS I_MotorVfd
   ```

   Код остаётся в форме CODESYS: Astra.IDE — сборка той же линейки CODESYS V3.5 SP17 (F01), и многое,
   что не описано у вендора, вероятно, работает. Маркер говорит, где смотреть, если сборка скажет иначе.
3. **Правки, без которых нельзя.** Только там, где известно наверняка, что CODESYS-форма в Astra.IDE не
   подойдёт, — каждая с маркером правки и причиной:

   ```
   // PORT: [comm] новый объект: Modbus RTU на REGUL — каналы Modbus Serial Outer Slave [F57, F58]
   PROGRAM PRG_ModbusMap_Regul
   ```

   Категории (`[oop]`, `[types]`, `[comm]`, `[lib]`…) — [port_metrics.md](port_metrics.md#методика).
4. **Проверка пометок и метрики:**

   ```bash
   python tools/port_metrics.py --orig my=upstream/my/src --adapted my=targets/astra/src --md build/my-metrics.md --json build/my-metrics.json --strict
   ```

   Код выхода 1 — есть правка без маркера (строка и файл — в выводе). Одинаковая метка `my` у
   оригинала и адаптированного дерева — сравнение только внутри пары.
5. **Файл импорта:**

   ```bash
   python tools/st_to_plcopen.py --root targets/astra --name my-project --out build/plcopen/my-project.xml --xsd auto
   ```

   Библиотеки — отдельными файлами и проектами-библиотеками в Astra.IDE, как здесь `targets/astra/lib`.

## 5. Сборка в Astra.IDE и закрытие пунктов

1. Проект REGUL мастером, библиотеки, импорт PLCopen XML, «Генерировать код» — по [BUILD_ERRORS.md](BUILD_ERRORS.md#цикл)
   и разделам 1–2 [чек-листа](migration_checklist.md).
2. Сообщения среды — новой итерацией в `BUILD_ERRORS.md`, у каждого — номер `N.k`, причина и решение.
3. Пункт подтвердился (например, `EXTENDS` собирается):

   ```bash
   python tools/port_checks.py --resolve C1 --note "2026-10-25, Astra.IDE 1.7.2.2: EXTENDS и SUPER^ собираются (BUILD_ERRORS 1)"
   ```

   Маркеры пункта удаляются из кода, решение записывается в файл решений.
4. Пункт не подтвердился:

   ```bash
   python tools/port_checks.py --fail C7 --note "BUILD_ERRORS 1.4: перечисление с базовым типом не принято"
   ```

   Теперь каждое место конструкции — ошибка `port_checks --strict`, пока код не переписан. Правки — с
   маркерами `// PORT: [types] BUILD_ERRORS 1.4: …`, их цена появится в `port_metrics`.
5. Повторять до сборки без ошибок; затем испытания по той же ПМИ (раздел 6 чек-листа, бланк —
   [test_protocol_astra.md](test_protocol_astra.md)). Трудозатраты в часах инженер записывает в README.

## 6. Когда исходный проект меняется

Источник переноса описан в `upstream/SOURCES.json`: `id`, рабочая копия оригинала (`repo`, переменная
`repo_env`), ревизия и коммит, каталог `subdir`, снимок `snapshot`, адаптированное дерево `target`,
исключения `exclude` (пути от `subdir`, например `POUs/PRG_Main/`) и замены `substitutions`. Для своего
проекта — своя запись. Дальше:

```bash
python tools/upstream_delta.py my --to main            # таблица: файл, изменение, копия в переносе, действие
python tools/upstream_delta.py my --to main --apply    # записать; снимок и коммит — на новую версию
python tools/port_checks.py --fix                      # маркеры у новых конструкций
python tools/port_metrics.py --strict
```

Копия, которую при переносе не правили, заменяется новой версией; правленая сливается трёхсторонним
слиянием `git merge-file` (общий предок — снимок), конфликт записывается с маркерами `<<<<<<< перенос …
>>>>>>> стало`. Подробно — [targets/astra/README.md](../targets/astra/README.md#когда-флагман-или-библиотека-обновились).

## 7. Пример: что вышло у КНС-1

Флагман КНС-1 (коммит `505ce14`) и библиотека plc-process-lib (`v1.0.0`), всё — до первой сборки в
Astra.IDE ([port_metrics.md](port_metrics.md)):

| Показатель | Значение |
|---|---|
| Значимых строк оригинала | 10 874 (флагман — 6 453, библиотека — 4 421) |
| Без изменений | 100 % |
| Новые объекты | 3 (68 строк): слой Modbus RTU для ПЛК REGUL |
| Маркеров проверки | 283; больше всего — C3 (спецификаторы доступа и свойства, 110), C11 (`LTIME`, 46), C7 (перечисления с базовым типом, 35), C13 (`VAR_IN_OUT CONSTANT`, 31), C5 (`strict`, 27), C1 (`EXTENDS`, `SUPER^`, 13) |
| Сборок в Astra.IDE | пока ни одной |

Чтение для оценки: дорогой сценарий — отказ C1–C4 (наследование ФБ и интерфейсов, 131 маркер `[oop]`,
иерархия из восьми ФБ библиотеки). Дешёвые — C3, C7, C13: механические правки по списку мест. Всё,
что зависит от устройства (Modbus, ввод-вывод, OPC UA, HMI), — ручные шаги в проекте, а не код.

## 8. Чего инструменты не делают

- Не компилируют и не проверяют код в Astra.IDE: это делает инженер; до записи в `BUILD_ERRORS.md`
  нигде не пишется «собирается в Astra.IDE».
- Не переносят визуализацию, задачи, дерево устройств, Modbus, символьную конфигурацию OPC UA и ссылки
  на библиотеки: PLCopen XML несёт только объекты раскладки.
- Правила `port_checks` находят конструкции по тексту строки: составные случаи (например, арифметику
  `LTIME` без литералов и преобразований) правило не видит — они проверяются сборкой.
- Факты о среде — на 16.10.2026 (Astra.IDE 1.7.2.x, пакет 1.7.2.6); новые версии среды надо сверять.
