## Исходники и сборка

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| B1 | Источник истины — тексты ST в `src/`, `.project` в git не хранится | принято | `.project` бинарный: его нельзя ревьюить и сливать. Готовые `.project` и `.library` прикладываются к релизам GitHub |
| B2 | Свойства в `build/assembled/` записываются в синтаксисе RuSTy: `PROPERTY_GET <Имя> : <тип> ... END_PROPERTY`, `PROPERTY_SET ...` | принято | В МЭК 61131-3 ред. 3 свойств нет; RuSTy понимает такой синтаксис. Собранный текст нужен только анализаторам и в CODESYS не импортируется |
| B3 | Вариант сборки `iec-checker` понижает конструкции, которые не разбирает iec_checker (методы внутри ФБ, `EXTENDS`, прагмы) | принято | Только для статанализа; семантика собранного текста может отличаться от исходной |
| B3a | Понижение может менять смысл ради разбора: `TIME()`/`LTIME()` → вызов заглушки `CDS__TIME()`, `a[i].x` → `a.x[i]`, вызов `afb[i](...)` → `afb(..., i)`, пустая ветвь → `CDS__NOP();`, невычисленная граница массива → `0..32767`, имена — ключевые слова iec_checker → суффикс `_` | принято | Иначе iec_checker 0.4 не разбирает весь файл (ParserError), и его находки теряются целиком. Проверено прогоном на копиях plc-process-lib (91 объект `src/` и `tests/`) и s7-to-codesys (54 объекта): ошибок разбора 0; у plc-process-lib, где таких конструкций в коде нет, набор находок тот же (1427 обоснованных, 176 артефактов), в копии с возвращёнными исходными формами (`Priority`, `LTIME()`, `afbAlarm[i](...)`, `a[i].x`, `WORD#1`, константы в границах) — тоже 0 ошибок разбора (до понижения — 6), а находки отличаются только на изменённых строках. Цена: часть находок не выдаётся (PLCOPEN-N3 у переименованных имён, OutOfBounds у невычисленных границ и массивов в `STRUCT`, PLCOPEN-CP13 у рекурсии методов) или выдаётся ложно (UnusedVariable у массива, к которому обращаются только как `a[i].x`). Список замен и их влияние — `tools/README.md`, «Понижение для iec_checker» и «Что понижение скрывает и добавляет» |
| B3b | Вариант сборки `rusty` понижает `VAR_IN_OUT CONSTANT` до `VAR_IN_OUT`; преобразования TIME ↔ целые объявлены в прокладке | принято | RuSTy 1.0.6 не знает модификатора (E034, E036 в вызовах) и этих преобразований (E048). Запрет записи в параметр и точность преобразований (в RuSTy `TIME` — 64 бит, нс; в CODESYS — 32 бит, мс) RuSTy не проверяет — их проверяет компилятор CODESYS (`cds.py build`, `check`) |
| B4 | GVL объявляются с `{attribute 'qualified_only'}`, обращение — `GVL_Const.ИМЯ` | принято | Рекомендуемая практика CODESYS: нет конфликтов имён. RuSTy не знает имён GVL — вариант сборки `rusty` убирает префикс `GVL_Const.` (проверено: `plc --check` по `build/assembled/rusty/` проходит) |
| B5 | Режимы разбираются `CASE` по перечислению (в шаблоне — `FB_Example` и `E_DeviceMode`; пример здесь удалён, правило остаётся для `targets/astra/src`) | принято | iec_checker 0.4 не разбирает метки `CASE` вида `E_DeviceMode.Auto` и неконстантные начальные значения (`:= E_DeviceMode.OutOfService`, `:= GVL_Const.ИМЯ`). Код пишется для CODESYS, а понижение — забота варианта сборки `iec-checker`: метки заменяются целыми значениями, неконстантные начальные значения убираются |
| B6 | Строковые литералы `STRING` (имена тестов, сообщения CfUnit) — только ASCII | принято | Кириллица в `STRING` зависит от кодовой страницы среды и рантайма. Комментарии остаются русскими |
| B7 | Обязательный статанализ в CI — iec_checker v0.4 (тот же, что локально); образ `nightly` — необязательное задание | принято | Обоснования в `iec_checker_allow.toml` подобраны под находки v0.4: с другой версией разборщика обязательная проверка зависела бы от его изменений. Бинарник v0.4 закреплён по размеру и SHA-256 (у релиза нет опубликованной суммы — она вычислена по файлу), образ `nightly` — по дайджесту |

## Инвентаризация (`tools/inventory.py`)

- **Читается зафиксированное состояние.** Исходники берутся из коммита (`git archive`), коммит
  записывается в `docs/inventory.md`. Библиотека — ветка `integrate` (выпуск 1.0: фундамент и все
  семейства ФБ), а если её уже нет — HEAD основной рабочей копии. Рабочая копия `integrate` ещё
  дорабатывается; отчёт должен повторяться по номеру коммита, поэтому незафиксированные правки в
  счёт не идут, а отчёт о них только предупреждает.
- **Пример шаблона не считается.** Объекты, побайтно совпадающие с `plc-repo-template`, пропускаются,
  как и задачи `config.json`, которые вызывают только такие объекты. Пока у флагмана в `src/` лежит
  только пример шаблона, его строка в отчёте пустая.
- **Счёт — по токенам `stlayout`:** комментарии, строки и прагмы как текст не считаются. Единица
  указана у каждой возможности: объект, член, секция `VAR…END_VAR`, переменная или вхождение.
- **Интерфейсный тип** узнаётся по интерфейсам сканируемых источников и по правилу имён `I_<Имя>`
  из CONTRIBUTING.md — так узнаются и типы библиотек, которые не сканировались (`PL.I_Motor`).
- **Библиотеки** узнаются по пространству имён (`Standard.`, `Util.`, `FILE.`, `coUnit.`, `PL.` и др.),
  по именам POU Standard, Standard64, Util и утверждений coUnit без пространства имён (списки сняты
  с `browsercache` библиотек установленного CODESYS 3.5.17.30) и по префиксам системных функций
  (`SysTime*`, `SysFile*`…). Имя, объявленное в коде (переменная `Mem`), библиотекой не считается.
  Области видимости не различаются: список объявленных имён общий для всех источников.
- **Риск** — по шкале отчёта и фактам исследования Astra.IDE. Возможность, которой в исследовании
  нет, получает «средний» риск с пометкой «в исследовании нет» и попадает в раздел «Не покрыто
  исследованием». Ключевые слова других сред — по лексерам RuSTy 1.0.6 и iec_checker 0.4; списки
  MasterSCADA 4D и «Полигона» не проверялись.

## Конвертер PLCopen XML (`tools/st_to_plcopen.py`)

- **Вариант CODESYS, а не «чистый» TC6.** Методы, свойства, интерфейсы, объединения, GVL и папки в TC6 2.01
  не описаны; файл пишет их в `addData` теми же расширениями `http://www.3s-software.com/plcopenxml/...`,
  что и экспорт CODESYS 3.5.17.30 (сняты экспортом той же фикстуры). По исследованию Astra.IDE пишет те же
  расширения (F46), поэтому выбран этот вариант.
- **Текст объявления в каждом объекте** (`interfaceasplaintext`). Импорт CODESYS берёт текст, а не
  структуру: объявления переносятся без потерь, это проверено сравнением текстов после импорта.
  Структурная часть остаётся для схемы и сред, которые читают только TC6 (`--no-plaintext`).
- **Пространство имён по умолчанию — `tc6_0201`**: задание требует версию 2.01, файл проверяется
  официальной схемой без замен, импорт CODESYS 3.5.17.30 принимает оба варианта. Экспорт CODESYS и
  Astra.IDE пишет `tc6_0200`; если Astra.IDE не примет `tc6_0201` — ключ `--namespace tc6_0200`.
- **Схема TC6 2.01 не хранится в репозитории**: условия распространения в файле с plcopen.org не указаны.
  Её скачивают в `build/xsd/` и сверяют по SHA-256 (`docs/plcopen.md`).
- **Persistent Variables создаются импортом PLCopen XML** в приложение (проверено на 3.5.17.30, в
  дополнение к D9: скриптом SP17 их создать нельзя). В пул POU такой объект не вставляется, поэтому
  проверка в режиме пула заменяет PVL на GVL с тем же текстом без `PERSISTENT` (как `cds.py check`).
- **`ARRAY[*]` и `REFERENCE TO`** записываются текстом в `derived`, как у CODESYS: в TC6 2.01 таких типов
  нет. Экспорт CODESYS без текстов объявлений пишет для `VAR_IN_OUT CONSTANT ... ARRAY[*] OF REAL`
  входной указатель с атрибутами, и его же импорт восстанавливает `VAR_INPUT CONSTANT ... POINTER TO REAL`
  (атрибут `Dimensions` — предупреждение C0351), а не исходное объявление (проверено на 3.5.17.30).
- **ObjectId** — UUID5 от вида, папки и имени объекта: повторная генерация даёт тот же файл, и дифф
  XML между коммитами показывает только изменения кода.
