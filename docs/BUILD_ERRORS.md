# Ошибки сборки в Astra.IDE

Журнал цикла исправлений переноса. Инженер импортирует адаптированный код в Astra.IDE, собирает
проект и вставляет сюда сообщения среды: ошибки импорта, компиляции, загрузки в ПЛК. По ним
исправляется код в `targets/astra/` (или конвертер PLCopen XML), а записи остаются как история:
закрытая запись получает статус и ссылку на коммит, но не удаляется.

**Журнал пуст: в Astra.IDE код ещё не собирался.** Первая итерация ждёт инженера — заготовка
[ниже](#итерация-1--гггг-мм-дд--импорт-и-сборка), заполняются только пустые поля.

Связанные документы: [migration_checklist.md](migration_checklist.md) (разделы 2, 8, 9),
[differences.md](differences.md), [port_metrics.md](port_metrics.md),
[targets/astra/README.md](../targets/astra/README.md) (что и с каких коммитов перенесено, как собрать).

## Цикл

1. **Подготовка итерации** (разработчик). Файлы импорта собраны из `targets/astra/` и проверены
   по схеме TC6 2.01 (их же собирает CI в артефакт `build-reports`):

   ```bash
   python tools/st_to_plcopen.py --root targets/astra/lib --name plc-process-lib --out build/plcopen/astra-lib.xml --xsd auto
   python tools/st_to_plcopen.py --root targets/astra --name kns-pump-station --out build/plcopen/astra-app.xml --xsd auto
   ```

   Коммит репозитория и имена файлов — в шапку итерации.
2. **Импорт и сборка в Astra.IDE** (инженер). Сначала библиотека: проект-библиотека, импорт
   `astra-lib.xml`, пространство имён `PL`, сборка, установка в репозиторий библиотек. Затем приложение:
   проект мастером Regul по чек-листу (раздел 1), библиотеки `PL`, Standard, CAA File, SysTimeRtc,
   импорт `astra-app.xml`, задачи по таблице сборки ВПЛК ([targets/astra/README.md](../targets/astra/README.md#две-сборки)),
   «Сборка → Очистить всё», затем «Сборка → Генерировать код» (в английском интерфейсе — Build →
   Clean all, Build → Generate code; названия пунктов в Astra.IDE сверить).
3. **Вставка сообщений** (инженер): шапка и блок `text` итерации. Сообщения — как есть, без
   сокращений: объект и позиция нужны для поиска.
4. **Разбор** (разработчик): у каждого сообщения — номер `N.k` (итерация N, сообщение k), причина и
   решение в таблице разбора. Решение — одно из:
   - правка в `targets/astra/` с маркером `// PORT: [категория] BUILD_ERRORS N.k: причина`;
   - ручной шаг в проекте Astra.IDE — в чек-лист миграции;
   - особенность среды — строка в `differences.md` со ссылкой на `N.k`;
   - непонятно, как ведёт себя среда, — новый пункт «проверить вручную» в чек-листе (раздел 9).
5. **Решения по пунктам «проверить вручную»** (разработчик). Пункт, который сборка подтвердила или
   опровергла, записывается в `targets/astra/port_checks.json`:
   - подтверждён — `python tools/port_checks.py --resolve C1 --note "ГГГГ-ММ-ДД, Astra.IDE <версия>: …"`:
     маркеры проверки этого пункта снимаются;
   - опровергнут — `python tools/port_checks.py --fail C1 --note "BUILD_ERRORS N.k: …"`: каждое место
     конструкции становится ошибкой `port_checks --strict`, пока код не переписан.
6. **Следующая итерация**: `tools/port_metrics.py --strict` (метрики и пометка правок), новые файлы
   импорта, снова шаги 2–5. Цикл закончен, когда сборка в Astra.IDE даёт 0 ошибок и все предупреждения
   разобраны — инженер подтверждает это в [сводке](#сводка).

**Метка маркера.** Категория маркера — по сути правки (`[oop]`, `[types]`, `[lib]`…), чтобы метрики
показывали, за что заплачено. `[build]` — только для правки, которая не подходит ни под одну
категорию (особенность компилятора). Ссылка `BUILD_ERRORS N.k` в причине обязательна в обоих случаях.

## Как скопировать сообщения

Astra.IDE построена на CODESYS V3.5 SP17 ([differences.md](differences.md), F01), поэтому окно
сообщений, по всей видимости, устроено так же, как в CODESYS; русские названия пунктов меню сверить в
среде.

1. Открыть окно «Сообщения» (в английском интерфейсе — View → Messages) и выбрать категорию:
   «Сборка» (Build) — для компиляции, категорию загрузки — для логина и загрузки в ПЛК.
2. Выделить все строки (Ctrl+A) и скопировать (Ctrl+C): копируются серьёзность, описание, проект,
   объект и позиция.
3. Сообщения импорта PLCopenXML (диалог или отчёт импорта) — скопировать текст; если копирование
   недоступно — переписать объект и текст сообщения, снимок экрана приложить к записи как файл
   в `docs/img/` (без данных лицензий и учётных записей).
4. Вставить в блок `text` итерации и заполнить шапку.

## Столбцы таблицы разбора

Шапку и блок `text` итерации заполняет инженер, таблицу разбора — разработчик.

| Столбец | Что писать |
|---|---|
| № | `N.k`: номер итерации и сообщения; на него ссылаются маркеры `// PORT:` и `differences.md` |
| Серьёзность | ошибка, предупреждение или сообщение — как в окне «Сообщения» |
| Код | код сообщения компилятора, если он есть (вид `C0000`) |
| Объект | POU, метод, свойство, GVL, DUT или устройство из сообщения |
| Позиция | строка и столбец из сообщения; для импорта — элемент XML |
| Сообщение (кратко) | суть по-русски, своими словами |
| Причина | категория маркера и причина; ссылка на пункт чек-листа (A1…K4) или факт [Fnn] |
| Решение | файл и маркер правки, ручной шаг (раздел чек-листа), строка `differences.md`, решение `port_checks` |
| Статус | открыто / исправлено в <коммит> / ручной шаг / особенность среды / проверить вручную (<пункт>) / принято (для предупреждения — с причиной) |

Пример строки (не реальная ошибка — так выглядит заполненная запись):

| № | Серьёзность | Код | Объект | Позиция | Сообщение (кратко) | Причина | Решение | Статус |
|---|---|---|---|---|---|---|---|---|
| N.1 | ошибка | C0xxx | FB_MotorVfd | строка 10 | не найден базовый ФБ | `[oop]` наследование не поддержано (C1) | композиция в `targets/astra/lib/src/POUs/Devices/FB_MotorVfd/`; `port_checks --fail C1` | исправлено в <коммит> |
